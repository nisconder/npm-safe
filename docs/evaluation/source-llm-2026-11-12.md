## 结果与分母

规则阳性定义为非运行故障类的 High/Critical 告警；模型阳性为引用校验通过的 `malicious`。本批规则的产品等级也全部为 `safe`，因此这里按产品等级计数的结果相同。`unknown`、无结果和准备失败均弃权，不当成安全，也不当成已检出。

模型的 3 个恶意弃权由 **2 个不确定 + 1 个准备失败**构成。正常弃权来自 ssh2 准备失败。16 份实际模型响应均通过 JSON 和原始源码引用校验；没有格式失败、引用失配或看到标签后的改答案。

- 以全部 6 个恶意尝试为分母，端到端检出率：规则 **0/6**，模型及联合 **2/6（33.3%）**。
- 只看成功准备的 5 个恶意包，模型检出 **2/5（40%）**；另有 2 个不确定，不能合并成“检出 4 个”。
- 排除不确定和准备失败后，模型已作出二元判断的恶意样本是 3 个，条件召回率为 2/3。这个较高数字不能代替前两项。
- 正常对照实际完成 11 个，双方均为 **0/11 误报**，其余 1 个未评审。样本量不足以证明普遍零误报。
- 全部尝试中的决策覆盖率：规则 16/18（88.9%），模型及联合 14/18（77.8%）。模型不确定属于有效响应，但不是二元决策。

联合策略只表示任一方阳性即报警；两方都阴性才是联合阴性。它不会消除规则已有的误报。本批规则没有阳性，所以联合结果与模型相同。

### 新增命中的证据边界

`bip40` 的 High 判断是“钱包恢复工具在安装时自动隐藏启动带嵌入式登录凭据的消息机器人”这一具有欺骗性的组合行为。完整 `install.js` 把 postinstall、子进程入口、隐藏输出及脱离父进程连接起来；入口片段包含消息客户端构造和令牌拼接登录。规则只给安装钩子与进程能力 Medium，所以最终仍是 safe / 84。

这个模型结果**没有证明完整远程命令授权链或密码外传**。它把另一个可见的 shell 执行分支列为 Medium，并明确命令来源、权限检查、部分发送参数没有提供。不能把研究报告描述的全部 RAT 能力冒充为本轮模型独立读出的事实。

`csbchalk-next` 的源码片段包含环境变量进入请求、返回码触发递归删除的连续链。删除目标包括源代码、版本控制目录和依赖，足以支持危险实现判断。但模型也发现编码 URL 解出后是 `ttps`，不是正常的 HTTPS 协议。**这个准确版本的请求、回调及删除能否实际成功没有得到证明**；本轮检出的是恶意实现/意图，不是现场可利用性验证。

敏感性检查：若因该运行缺陷单独排除 `csbchalk-next`，成功准备的恶意集合剩 4 个，规则检出 0/4，模型检出 1/4、2 个不确定、1 个漏报；正常误报仍为 0/11。正式结果不删除这个预先选定样本。

## 准备与覆盖限制

`types-node` 超过预先设定的研究 ZIP 下载上限，下载被终止，准确版本的包内 manifest 没有核验。`ssh2` 的官方归档根目录是 `mscdex-ssh2-d5c97b4/`，准备脚本假定 `package/`，因此未能生成输入。这是**本轮数据准备脚本的兼容问题**，不能据此推断规则扫描器本体无法处理该包。两者没有换包补位，也没有当成阴性。

16 个生成证据的归档，其规则深扫与原型归档读取均报告 complete；**16 个模型证据视图均为 partial**。归档读完不等于模型看过完整源码。所有证据包共提供 419,970 个 UTF-16 字符，单包 4,480–38,462 字符，包含源码、原始 manifest 与少量 README；这是证据包大小，不是 API token 数或人工验证过的阅读量。

原型默认预算为每包 40,000 字符、16 文件、每源码文件 8,000 字符；原始 manifest 至多 2,000、README 至多 1,200。归档上限、解码上限与这些模型视图上限独立记录。原型优先入口、安装脚本、相对引用与能力窗口，不依赖已有规则是否报警，仍可能漏掉整个文件或把有用调用链切断。

### 揭盲后的覆盖诊断

以下是读取完整归档后做的事后诊断，没有提供给盲审实例，也没有用于修改本轮答案。位置采用原始文件 UTF-16 offset，区间右端不包含。

- **miso-client 漏选整个载荷文件。** `package/dist/express/error-types.js` 共 21,995 字符，94 行 offset 3486 处出现 Unicode variation-selector 解码器，95 行 offset 3666 起是解码后交给 `eval` 的表达式。该文件虽被采集器识别为可达且带编码/动态行为，但排序第 54，落在 16 文件上限外；多种正常网络/认证信号的累计分反而更高，类型声明入口也占用了名额。模型完全没有看到这段载荷，不能把此次漏报描述为“模型看到了恶意代码却不理解”。整个流水线仍然算漏报，模型 `benign` 不能当作完整包的结论。
- **gluestack 有两种预算浪费。** 4,694 字符的 `package/lib/index.js` 在单遍均分中只拿到 2,560 字符额度；窗口重叠合并后实际只提供 1,890 字符，且没有补足。后续小文件用不满的额度也不会回填前面的入口，所以全包只用了 12,818/40,000 字符。入口只提供 `[0,640)`、`[1077,1815)`、`[4182,4694)`；缺口 `[1815,4182)` 包含关键函数定义与大量编码文本，模型无法解析调用链。
- **solana 的关键连接落在缺口里。** 全部 6 个候选文件都入选，但只显示 34,433/150,872 个已解码字符，每个 JavaScript 文件都被截断。`package/dist/index.js` 中 offset 35857 的 Worker 动态执行点与 offset 58614 的 `form.pipe(req)` 都没提供，无法连接嵌入文本、执行和上传；安装脚本中构造执行文件及参数的部分也被截掉，模型只看到后面的后台启动。

这三项分别支持下一轮改进文件优先级、预算回填和按引用补齐调用链。它们不证明补齐后模型一定判对；需要另一个冻结版本和新的对照实验。

## 对后续工作的含义

源码模型已经补出了规则没连接起来的上下文行为，并在这 11 个正常对照上没有新增误报。但它仍然会漏报，也会因为证据不够而无法判断。优先研究如何完整送达相关入口、载荷和调用链，并让模型在有实质缺口时请求补充证据，再用另一批未见样本验证。保留本轮原始结果，后续变化应另起版本和实验；目前不应让模型的 `benign` 覆盖规则报警或当成整个包的安全保证。
