# Known-miss repairs and benign regression checks — 2026-11-12

This is an unreleased-source regression comparison, not an independent accuracy
benchmark. The five newly acquired malicious versions were inspected before
these repairs. All 26 versions below are now observed development data, even
where an older dataset retains its historical `test` label. Do not count them
as a future blind test set.

The comparison uses the same frozen artifacts before and after the change,
with default rules, no cache, no LLM, and no package installation or execution.
The offline harness reads archives in memory. Eight malicious samples are
source repacks from the DataDog archive, not original npm tarballs; source
bytes were preserved and hashed, but original npm SRI is not claimed for these
repacks. The 18 provisional benign controls use official npm tarballs with
their published integrity metadata. Benign labels do not imply freedom from
ordinary vulnerabilities.

## Changes under test

- Private-key/seed flow into fetch headers or body, including bounded helper
  calls and recognized reversible encodings. Public keys, signatures, hashes,
  redacted values and unrelated network use are negative cases.
- HTTP download to a file, optional extraction, then a connected detached
  process with ignored stdio. Ordinary download/build capabilities alone do
  not establish this signal.
- Restricted constant string-table recovery that reveals concealed process
  execution together with actual file reads and network calls. Source is never
  evaluated to recover the strings.
- Text-file capacity increased from 1 MiB to 4 MiB; lexical capacity from
  200,000 to 1,600,000 tokens. The 8 MiB aggregate text limit remains. Exhausted
  archive/lexical budgets still produce partial results.
- A High finding makes a complete scan at least `suspicious`, without changing
  severity weights. Critical findings remain `dangerous`; incomplete scans
  without established danger remain `unknown`. Scanner cache identity is 5.

The pre-change snapshot already contains the lodash dynamic-execution fix;
this comparison measures whether the subsequent repairs introduce new alerts.

All 18 normal controls remain `safe` after repair, with zero high/critical
alerts. Esbuild retains its expected Medium install/process findings (84);
node-gyp, cross-spawn and core-js retain Medium findings (92). The other
controls score 100. This includes lodash and the two clean wallet SDKs.
WalletConnect and clean xrpl change from partial/unknown to complete/safe.
The existing three malicious regressions retain their previous scores and
positive classifications.

Metadata-only checks still label all eight malicious versions `safe` in this
corpus. These improvements require deep scanning; they do not improve the
default metadata-only inspection boundary. Also, `suspicious` is below the
default CI failure threshold of `dangerous`; use `--fail-level suspicious`
when High findings should fail CI. Install-score thresholds are unchanged.

The final serial run used Windows x64, Node 24.22.1. The largest malicious
bundle completed in about 3.56 seconds. Peak RSS for the entire serial
26-version evaluation process was 651,380 KiB (about 636 MiB); this is not
a per-file allocation measurement or a universal performance bound. Larger
limits and additional analysis have a real memory/time cost.

## Verification

- Core type checking and TypeScript build passed.
- Full core test run: 684 tests, 682 passed, 2 skipped, 0 failed.
- Evaluation/partition harness: 12 tests passed, 0 failed.
- `git diff --check` passed.

Negative cases cover ordinary SDK/RPC payloads, signatures/hashes, object
redaction and reassignment, callback/parameter/block shadowing, disconnected
download paths, ordinary build processes, duplicate spawn options and inert
documentation strings. Archive-level tests also check encoded property names
through the prefilters, evidence past the old file/token limits, and visible
partial results beyond the new limits. Changes remain local and unreleased.

## Limits of the result

`complete` describes bounded archive/text inspection, not exhaustive behavior
coverage. Unsupported syntax, arbitrary runtime decoding, cross-file flow,
different network APIs and native code can still hide malicious behavior.
The tinycolor alert remains the existing sensitive-environment/network
co-occurrence rule after the previously skipped bundle becomes inspectable;
it does not trace the complete credential-exfiltration chain.

The download rule does not establish runtime control flow or verify artifact
signatures; a legitimate silent updater can trigger it. Legitimate software
that conceals process/file/network capabilities can also require review.
Private-material detection uses constrained syntax and names rather than a
complete type system. No package, version, domain or sample-hash allowlist was
added. A zero-alert result on these selected controls cannot establish a zero
false-positive rate in the npm ecosystem.

`.npm-safe/scanner-fixes-20261112/`; malicious source is not committed.

per-package findings and scan outcomes without embedding malware source.
