# Six-version scanner pilot — 2026-10-31

Deep scanning flagged **one of three selected malicious versions**; metadata
scanning flagged none at either declared detection policy. Both modes left the
three provisional benign controls negative. This small, deliberately selected
pilot establishes reproducible failure cases; it does not estimate npm-wide
precision, recall or safety. No scanner rules or thresholds were tuned.

The [frozen manifest](pilot-2026-10-31.dataset.json) and
[sanitized results](pilot-2026-10-31.results.json) preserve coordinates, source
attribution, hashes, decisions, counts and timings. Package artifacts and raw
finding snippets are not distributed with this report.

## Samples and evidence

| Incident / split | Malicious version | Provisional control | Label source |
| --- | --- | --- | --- |
| July 2025 phishing / dev | eslint-config-prettier 10.1.7 | 10.1.5 | [Project incident discussion](https://github.com/prettier/eslint-config-prettier/issues/339), [reviewed advisory](https://github.com/advisories/GHSA-f29h-pxvx-f335) |
| Same July incident / dev | is 3.3.1 | 3.3.0 | [Socket original investigation](https://socket.dev/blog/npm-is-package-hijacked-in-expanding-supply-chain-attack) |
| September 2025 phishing / test | debug 4.4.2 | 4.4.1 | [Maintainer security advisory](https://github.com/debug-js/debug/security/advisories/GHSA-4x49-vf9v-38px) |

All versions and controls from one incident stay in one split. The test split
contains **one positive, one negative and one incident**. It is a reserved
pilot case, not an adequately sized final benchmark. Controls were selected
from preceding versions outside the cited malicious releases, with static
entry-point/lifecycle review; their benign labels remain provisional.

Malicious source archives are attributed to
[DataDog/malicious-software-packages-dataset at commit 3fc8a1f](https://github.com/DataDog/malicious-software-packages-dataset/tree/3fc8a1ff23fadb612234526e31a60e24bbc0bb3e),
an Apache-2.0 dataset. Its detection-led collection is a selection-bias risk.
All three malicious inputs are deterministic, byte-preserving **source
repacks**, because those archives contain package files rather than original
npm tarballs. They cannot measure published SRI or original archive structure.
The three controls are original Registry tarballs independently checked
against SHA512 SRI and SHA1. Package code and lifecycle scripts were never
executed; no samples were installed or contacted.

## Decisions and matrices

The protocol was fixed before scanning: `highCritical` is any high/critical
behavioral finding; `productLevel` is `suspicious` or `dangerous`. A completed
`safe` product report is negative. Partial/failed scans abstain for both
policies; product `unknown` also abstains. In this run the two policies produced
the **same matrices**:

| Split | Mode | TP | FP | TN | FN | Abstentions | Recall on these positives |
| --- | --- | ---: | ---: | ---: | ---: | ---: | --- |
| dev: 2 positive, 2 negative | metadata | 0 | 0 | 2 | 2 | 0 | 0/2 |
| dev: 2 positive, 2 negative | deep | 1 | 0 | 2 | 1 | 0 | 1/2 |
| test: 1 positive, 1 negative | metadata | 0 | 0 | 1 | 1 | 0 | 0/1 |
| test: 1 positive, 1 negative | deep | 0 | 0 | 1 | 1 | 0 | 0/1 |

All 12 requested scans completed; partial/failed proportions were 0/4 for
each dev mode and 0/2 for each test mode. Deep mode added one TP and zero FP
in dev and changed no decision in test. Precision is undefined when no
positives are predicted; deep dev had one predicted positive and it matched
the label. Three selected controls with zero FP do not support a general
false-positive or precision claim.

## Per-version results and failure analysis

| Version | Split / label | Metadata score, level, rules | Deep score, level, rules |
| --- | --- | --- | --- |
| eslint-config-prettier 10.1.7 | dev / malicious | 92, safe; install-script (medium) | 89, safe; install-script (medium), content-native-binary (low) |
| eslint-config-prettier 10.1.5 | dev / control | 100, safe; none | 100, safe; none |
| is 3.3.1 | dev / malicious | 92, safe; install-script (medium) | 77, suspicious; install-script (medium), content-obfuscated-exec (high) |
| is 3.3.0 | dev / control | 100, safe; none | 100, safe; none |
| debug 4.4.2 | test / malicious | 100, safe; none | 100, safe; none |
| debug 4.4.1 | test / control | 100, safe; none | 100, safe; none |

**eslint-config-prettier 10.1.7 is a false negative under both policies.**
The scanner noticed its install hook and DLL, but these are medium/low
capability findings. Independent in-memory byte checks confirmed that
`install.js` constructs the child-process module, spawn property and Windows
loader name from string fragments, which the scanner's literal process
patterns miss. This agrees with the original project incident discussion.
The 5,806-byte file was below the text limit and contained no NUL byte. The
scoring rule subtracts 8 for medium and 3 for low: 100 − 8 − 3 = 89, still
`safe` (threshold 80). An install-hook notice alone is not a high alert or a
malware decision. [Original incident evidence](https://github.com/prettier/eslint-config-prettier/issues/339)

**debug 4.4.2 is a false negative under both policies.** Its malicious version
has no install hook. The changed `src/index.js` grows from 314 to 76,754 bytes
and remains within the content limit. The scanner reported no matching
content rule. Independent static review found browser networking/wallet
primitives and indirection, while the maintainer describes browser-context
cryptocurrency redirection. This exposes a behavioral coverage gap in the
current Node process/encoded-execution predicates; no runtime effect was
tested here. [Maintainer impact description](https://github.com/debug-js/debug/security/advisories/GHSA-4x49-vf9v-38px)

**is 3.3.1 is detected only by deep mode.** Metadata sees a generic postinstall
hook. Deep inspection finds obfuscated dynamic execution in the 822,345-byte
`test/check.js`, adding a high finding: 100 − 8 − 15 = 77 (`suspicious`). The
path being named `test/` did not suppress this obfuscation rule. This is
evidence of an additional signal, not dynamic proof of the reported loader's
full behavior. [Original investigation](https://socket.dev/blog/npm-is-package-hijacked-in-expanding-supply-chain-attack)

Deep reports marked integrity verified for all three controls and false for
all repacks, as expected. Complete parsing still skipped 2–4 non-text files
per archive; it does not imply semantic inspection of native binaries.

## Timing and reproduction limits

Run time: 2026-10-31 16:31:41 Asia/Shanghai; Node v24.22.1, Windows x64,
core 1.1.1, tsx 4.23.13. Current TypeScript source was scanned with default
rules, no cache/config overrides/plugins/LLM. Each version/mode ran once,
serially. Nearest-rank percentiles in milliseconds:

| test / metadata | 2 | 0.343 | 2.121 | 6.047 | 8.223 |

Scanner time excludes input reads, hashing and JSON parsing; wall time includes
them. Both exclude acquisition, process startup and loader startup. These tiny
single-run observations are not a stable performance benchmark. Source hashes
and exact timings are in the sanitized JSON.

To rerun, independently prepare a separate corpus directory from the pinned
sources and derivation recorded in the manifest, then copy the frozen manifest
there as `dataset.json`; its artifact paths are relative to that directory.
Use the [offline command and protocol](../evaluation.md), writing to a new
results file. The original artifact acquisition/repack helpers and raw reports
remain local evidence. The prepare helper refreshes capture timestamps, so
rerunning it must not replace the frozen manifest. This repository therefore
supports verification against declared hashes, not one-command corpus
reconstruction. Selected artifacts all downloaded successfully; exploratory
unselected candidates were recorded separately before evaluation.

Next work should validate these two missed behaviors against more independently
labeled incidents and legitimate controls before choosing rules, constant
folding/AST analysis or other approaches. The present test case has now been
inspected; subsequent tuning requires a new reserved evaluation set.
